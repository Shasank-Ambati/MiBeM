Programming and workflow

Computational work is as much about organisation as about equations: running many calculations, keeping track of what produced which result, and being able to repeat it months later. This page covers the practical skills that make that routine: the command line, a scripting language, version control, clusters and testing.

After reading this page you should be able to:
  • Move around and automate tasks from the command line, including simple loops and pipes.
  • Read data, fit and plot it in Python with NumPy, SciPy and Matplotlib.
  • Keep a project under version control and describe a reproducible folder layout.
  • Submit and manage jobs on a cluster scheduler, and test a piece of your own code.

Starting point: If you have never programmed, start with Your first simulation, which introduces Python step by step and runs in a browser, then come back here for the working habits.

2. The command line#

A shell reads commands, runs programs and glues them together. On Linux and macOS it is built in; on Windows, the Windows Subsystem for Linux (WSL) provides one. Everything is addressed by paths: absolute paths start at the root (/home/you/project), relative ones from the current directory, with . for the current and .. for the parent directory. The most useful commands:

TaskCommands
Navigate and listpwd, cd, ls -l
Create, copy, move, deletemkdir, cp, mv, rm (deletion is permanent: there is no recycle bin)
Look at filescat, less, head, tail, wc -l
Searchgrep (text inside files), find (files by name or date)
Comparediff, sort, uniq
Remote machinesssh to log in; scp and rsync to copy files
Processestop, ps, kill

Two ideas give the shell its power. A pipe sends the output of one command into the next, and > redirects output to a file. A loop repeats a command for many cases. Together they turn a morning of clicking into a line:

# last total energy printed in a VASP OUTCAR file
grep "free  energy   TOTEN" OUTCAR | tail -1

# make one folder per temperature
for T in 300 600 900; do mkdir T$T; done

Environment variables (such as PATH, the list of places searched for programs) and courses (course load lammps on most clusters) control which software versions you get. Python and other packages are managed in isolated environments (python -m venv, or conda / mamba), so that one project’s libraries do not break another’s.

3. Python for science#

Python is the usual glue language: readable, with a large scientific ecosystem. The core is small. Lists and dictionaries hold data, loops and functions structure the work, and f-strings format output. The scientific stack adds:

  • NumPy: fast arrays with vectorised operations (apply a formula to a million numbers without writing a loop), slicing and broadcasting (arrays of different shapes combine by stretching the smaller one).
  • SciPy: linear algebra, optimisation, integration, interpolation, statistics and ODE solvers (see numerical methods).
  • Matplotlib: plots; pandas: tables of mixed data; Jupyter notebooks for exploring and documenting.
  • Materials-specific libraries: ASE and pymatgen (structures and workflows), pycalphad (thermodynamics), matminer and scikit-learn (machine learning).

A typical job reads data, computes, writes a result and plots it. This script fits the Arrhenius law (see diffusion and kinetics) to tabulated diffusivities and then evaluates it:

import numpy as np

kB = 8.617333e-5                 # eV/K
D0, Q = 2.0e-6, 0.87             # m^2/s, eV (illustrative values)
T = np.linspace(500, 1000, 6)    # K
D = D0 * np.exp(-Q / (kB * T))   # vectorised: no loop needed

for t, d in zip(T, D):
    print(f"{t:6.0f} K   D = {d:.2e} m^2/s")

# fit ln D against 1/T: the slope is -Q/kB
slope, intercept = np.polyfit(1 / T, np.log(D), 1)
print("recovered Q =", -slope * kB, "eV")

And turning a molecular-dynamics mean-squared displacement into a diffusion coefficient (see molecular dynamics) takes four lines. Conversions are a classic source of mistakes: 1 Å²/ps = 10−8 m²/s.

import numpy as np

data = np.loadtxt("msd.dat")                 # columns: time (ps), MSD (A^2)
t, msd = data[:, 0], data[:, 1]
slope, intercept = np.polyfit(t, msd, 1)     # MSD = 6 D t  in three dimensions
print(f"D = {slope / 6 * 1e-8:.3e} m^2/s")

4. Units and data formats#

Unit systems differ between programs (see physics for simulation), so write the unit next to every number: in column headers, variable names and file comments. File formats matter for exchange and long-term use.

5. Version control#

Git records the history of a project as a series of snapshots (commits), each with a message saying why it changed. It lets you return to any earlier state, try ideas on separate branches, compare versions with git diff, and share work through a remote such as GitHub or GitLab. A basic session:

git init                      # start tracking this folder
git add run.py in.lammps      # choose what goes in the next snapshot
git commit -m "Add vacancy-formation input and run script"
git status                    # what has changed
git log --oneline             # the history
git switch -c larger-cell     # try something on a new branch
git push                      # share it

What to track: scripts, input files, notes, small data and the instructions to rebuild the rest. What to leave out: large outputs (trajectories, wavefunctions), temporary files, binaries and anything secret such as passwords or access keys; list them in a .gitignore file and describe how to regenerate them in the README. Write commit messages that say why, make commits small and focused, and tag the commit that produced each published figure.

6. Running on a cluster#

You log in to a login node to prepare and submit work (never run heavy calculations there) and a scheduler, most often Slurm, places your job on compute nodes when resources are free. A job is described by a batch script whose #SBATCH lines request resources:

#!/bin/bash
#SBATCH --job-name=cu_vac
#SBATCH --nodes=1
#SBATCH --ntasks-per-node=32
#SBATCH --time=02:00:00
#SBATCH --output=%x_%j.out

course load lammps
srun lmp -in in.vacancy

Submit it with sbatch job.sh, watch it with squeue -u $USER, cancel with scancel <jobid> and review finished jobs with sacct. A job array runs the same script for many parameter values, for example ten temperatures:

#SBATCH --array=0-9
T=$((300 + 100 * SLURM_ARRAY_TASK_ID))     # 300, 400, ... 1200 K
srun lmp -in in.melt -var T $T

Good practice on shared machines:

  • Test small first, then measure how the run time scales with core count before requesting hundreds of cores (see parallel scaling).
  • Ask for what you need. Requests far above the need wait longer in the queue; a time limit set too short kills the job. Allow a safety margin of 20–30% on measured run time.
  • Checkpoint long runs (write restart files regularly) so a failure costs hours, not days.
  • Mind the file systems. Fast scratch storage is for running jobs and is often purged; home or project storage is for keeping results. Copy what matters off scratch, and compress or delete bulky intermediate files.
  • Read the error first. The usual failures are out of memory, exceeded time limit, a missing course or a wrong path, and the scheduler and program logs say which.

7. Workflows and reproducibility#

A reproducible result is one that you, or someone else, can regenerate from recorded inputs. That needs organisation more than clever tools.

  • A predictable folder layout, one project per directory with separate places for inputs, scripts, raw output and results. A common structure: inputs/, scripts/, runs/<case>/, results/, notes.md.
  • Scripts, not clicks. Generate input files and run sweeps from a script, so changing a parameter and re-running is one command. Notebooks are excellent for exploring; move stable steps into scripts.
  • Record the environment: code versions, library versions (pip freeze, conda env export), the potential or pseudopotential files used, the random seeds, and the units. Containers (Docker, Apptainer) freeze a whole software stack.
  • Name things consistently, with parameters in directory names (Cu_vac_4x4x4_T300) or, better, recorded in a metadata file next to the output.
  • Workflow managers (Snakemake, AiiDA, signac, jobflow) automate dependencies between steps and store provenance; they pay off once a project has hundreds of calculations.
  • Share and archive the inputs and scripts behind a paper in a repository that issues a persistent identifier (Zenodo, Materials Cloud). Data that are findable, accessible, interoperable and reusable (the FAIR principles) are worth more than data that are merely posted.

8. Testing your code#

Research code is easy to get quietly wrong. Cheap checks catch most errors before they reach a paper:

  • Test against known answers: analytic solutions, limiting cases, textbook numbers, a published benchmark.
  • Check invariants: conserved energy or mass, symmetry, correct units, results that must be positive or monotonic.
  • Automate it with unit tests that run in one command, so a later change that breaks something is noticed at once. With pytest, a test is a function whose name starts with test_:
import numpy as np

def arrhenius(T, D0, Q, kB=8.617333e-5):
    return D0 * np.exp(-Q / (kB * T))

def test_arrhenius_limits():
    assert np.isclose(arrhenius(1e12, 2.0, 0.9), 2.0, rtol=1e-6)   # very high T gives D0
    assert arrhenius(300, 2.0, 0.9) < arrhenius(600, 2.0, 0.9)      # rises with temperature

Compare floating-point numbers with a tolerance, never with ==. Keep a small regression test that reruns a quick case and compares with a stored result, so changes in a library version or a refactor that alter results are flagged.

9. Debugging and habits#

  • Read the error message from the bottom up. The last line says what failed, the lines above say where.
  • Make a minimal example that reproduces the problem; half the time the bug is found while shrinking it.
  • Print, log or plot intermediate values and look at them; use a debugger (pdb, or the one in your editor) for harder cases.
  • Change one thing at a time, and keep the working version in version control.
  • Profile before optimising (python -m cProfile): the slow part is rarely where you expect.
  • Write for the next reader: clear names, short functions, a README that says how to run the project and what each file is. The next reader is usually you, six months later.
  • Back up anything that cannot be regenerated, on more than one machine.

For viewing results, common tools are VESTA and OVITO (structures and defects), ParaView (fields and meshes) and Matplotlib (plots), with VS Code, PyCharm or a terminal editor for writing code.

Key takeaways
  • A scripting language (Python with NumPy, SciPy and Matplotlib) plus the command line covers most day-to-day computational work.
  • Keep inputs, scripts and notes under version control; keep large outputs elsewhere and record how they were made.
  • On a cluster, test small, request only the resources you need, use job arrays for parameter sweeps and checkpoint long runs.
  • Reproducibility means recorded versions, seeds, units and inputs so that someone else, or you in a year, can rerun the work.
  • Test your own code against analytic solutions and simple limits before trusting it on real problems.

10. Check your understanding#

What does grep "TOTEN" OUTCAR | tail -1 do?

grep prints every line of the file OUTCAR containing “TOTEN”; the pipe passes those lines to tail -1, which keeps only the last one, here the final total energy of a calculation.

A calculation takes about 3 hours when measured. What time limit would you request, and why not 48 hours?

About 4 hours: a margin of 20–30% protects against variation without wasting the allocation. A 48-hour request would wait much longer in the queue, block resources and can be rejected by queue limits, and it gives no benefit.

Which files belong in a git repository for a simulation project, and which do not?

Track scripts, input files, notes and small reference data, plus instructions to regenerate everything else. Leave out large outputs such as trajectories and wavefunctions, temporary files, binaries and secrets; record in the README how to recreate them.
